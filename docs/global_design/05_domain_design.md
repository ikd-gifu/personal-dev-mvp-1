# ドメイン設計書

## エンティティ

| エンティティ   | 説明                                    | 主な属性（プロパティ）                                                                                                                   |
| -------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Account  | 登録済み、ログインしているユーザー<br>Note、Templateを作成 | `id`、`firstName`、`lastName`、`email`、`thumbnail`、`createdAt`、`updatedAt`、`isActive`、`provider`、`providerAccountId`、`lastLoginAt` |
| Template | 複数の項目（Field）を持つ<br>これを元にNoteを作成       | `id`、`fields[]`、`ownerId`、`updatedAt`、`name`                                                                                  |
| Field | Templateの1つの入力項目 | `id`、`label`、`order`、`isRequired`※ |
| Note     | Templateを元に作成<br>設計メモ1件               | `id`、`title`、`ownerId`、`sections[]`、`templateId`、`createdAt`、`updatedAt`、`status`                                             |
| Section  | Noteの1つの項目                            | `id`、`content`、`fieldId`                                                                                                      |
| Status   | ノートの状態<br>下書き（Draft）か公開（Publish）      | `draft`、`publish`                                                                                                             |

> ※ `isRequired`（必須かどうか）は、テンプレートが定義する構造情報として保持する。
> **MVPでは必須チェックはノート作成・編集フォームの入力バリデーションのみで行い、ドメイン層では検証しない。**
> そのため、API経由では必須項目が空のノートも作成できる（MVPでは許容する割り切り）。
> 将来「必須項目が空なら公開できない」をビジネスルールに昇格させる場合は、`canPublish`側でチェックする。

## VO（Value Object）

| 名前     | 使う場所            | 守るルール（ほんの少しの約束）                | 例                   | 備考                         |
| ------ | --------------- | ------------------------------ | ------------------- | -------------------------- |
| Email  | `Account.email` | 「@」が必ずある<br>空NG<br>前後の空白をトリムする | `example@email.com` | みんなで同じルールを使い、間違うと困るのでVOにする |
| Status | `Note.status`   | Publish／Draftのみ          | Draft／Publish       | アプリの意味が強い（公開／下書き）のでVOにする   |

## 集約

| チーム名（集約）               | 集約ルート（リーダー） | 中にいるメンバー（子エンティティ・VO）                                  | 外との関係・使い方                                    | チームの役割（ざっくり）                                      |
| ---------------------- | ----------- | ----------------------------------------------------- | -------------------------------------------- | ------------------------------------------------- |
| Accountチーム             | Account     | Email（VO）<br>プロバイダー情報（`provider`、`providerAccountId`） | Note／Templateを所有する                           | OAuthでログインしたユーザーを表すチーム<br>他チームの親（所有者）             |
| Templateチーム            | Template    | Field（入力欄の定義）                                         | Accountに属する（Owner）<br>Noteから利用される            | ノートの型（構造）を定義するチーム<br>Templateがリーダーで、Fieldがその中のパーツ |
| Noteチーム                | Note        | Section（本文の各パート）<br>Status（状態）                        | Templateを参照する（どの型で書くか）<br>Accountに属する（Owner） | テンプレートを使って1件のノートを作るチーム<br>Noteがリーダーで、Sectionは中身   |
| 共通VO（どのチームにも属さない小さな部品） | なし（単独）      | Email（Account用）<br>Status（Note用）                      | 各チームで使われる                                    | 共通ルール                                             |

## 関係図

```text
[Account]──owns──>[Template]──contains──>[Field]
    │
    └──owns──>[Note]──contains──>[Section]
                    │
                    └──uses──>[Template]
```

## ドメインロジック

### Noteチーム（ノートの世界）

| ルール                                | なにをしてる？                             |
| ---------------------------------- | ----------------------------------- |
| NoteはTemplateを元に作成する               | ノートが「テンプレートがないと書けない」と決めている          |
| ノートを消したら中のセクションも一緒に消す              | ノートが親分で、セクションはその子<br>親が消えたら子も一緒に消える |
| ステータスは「下書き」か「公開」だけ                 | ほかの言葉（例：プレビュー）は使えない<br>2つの状態しか持たない  |
| ステータスを変えられるのはオーナーだけ（判定だけ）          | 誰が変えられるかをノートの中で判断する<br>「自分のノートだけOK」 |
| 新しいノートを作るとき、テンプレートの項目からセクションを自動で作る | テンプレートの「書く欄」を読んで、ノートが自分の中に欄をコピーする   |
| Note作成時に指定したTemplateは後から変更できない | ノートを作るときに決めた`templateId`は変更不可<br>途中で型を変えるとセクションと項目が食い違ってしまうため |

### Templateチーム（テンプレートの世界）

| ルール                            | なにをしてる？                            |
| ------------------------------ | ---------------------------------- |
| Field（項目）の順番はかぶらない             | テンプレートの中で、1番・2番・3番が重ならないように並べる     |
| Field（項目）の名前は空じゃダメ             | 「問題」「決定」など、欄の名前がないと使えないため          |
| Fieldの追加・削除・並べ替えはテンプレートがまとめて行う | 子どものFieldを勝手に触れないように、親のテンプレートが管理する |
| 利用中のテンプレートは削除できない | Noteから使われているテンプレートを消すと、そのノートが型を失ってしまう<br>「使われているか？」の確認はNoteチームへの問い合わせが必要なので、判定はアプリケーションサービスで行う |

### Accountチーム（アカウントの世界）

| ルール                                         | なにをしてる？                       |
| ------------------------------------------- | ----------------------------- |
| 少なくとも名前（`firstName`）か苗字（`lastName`）のどちらかは必須 | 誰か分からないため、最低でも名前か苗字のどちらかは必要   |
| `provider` + `providerAccountId` の組み合わせは一意  | 同じOAuthプロバイダーで同じアカウントIDは1つだけ  |
| アカウントは自分のノートとテンプレートを「持つ」                    | 自分のものだけを見たり直したりできるように関係を持っている |
| ログイン時にプロフィール情報と最終ログイン時刻を更新                  | OAuthログイン時に最新のプロフィール情報で更新する   |

### 共通ルール（どのチームでも同じ）

| ルール                                            | なにをしてる？                   |
| ---------------------------------------------- | ------------------------- |
| 子ども（SectionやField）は、親（NoteやTemplate）を通してしか触れない | 外から直接いじれないように、親がまとめて面倒を見る |
| チームの中のモノは、チームごとに保存・変更する                        | 別のチームのデータを勝手に直さないようにしている  |

## ドメインサービス

| サービス名                        | どんな仕事？                                                  | 関わるドメイン（集約）  |
| ---------------------------- | ------------------------------------------------------- | ------------ |
| `canPublish(note, account)`  | ノートを「下書き→公開」にしてよいかを判定する<br>オーナーならOK、他人ならNGという条件をチェックする係 | Account、Note |
| `canUnpublish(note, account)` | ノートの公開を取り消せるかを判定する<br>オーナーならOK、他人ならNGという条件をチェックする係      | Account、Note |

> **ドメインサービスに置くものの基準**
>
> * ドメインサービスは、**ロード済みの集約だけを見て判定できる純粋なルール**のみを置く（DBアクセスなし）。
> * リポジトリへの問い合わせが必要な判定（例：Template削除時の使用チェック）は、**アプリケーションサービス**で行う。

## 集約境界とトランザクション境界

### 集約とトランザクションの関係

* このシステムでは、**集約（Aggregate）の境界 = トランザクション境界**とする。

| 集約       | トランザクション対象       | 理由                                       |
| -------- | ---------------- | ---------------------------------------- |
| Account  | Accountのみ        | 単一エンティティで完結する<br>他のエンティティとの同時更新は不要       |
| Note     | Note + Section   | ノートと各セクションは一体で管理する<br>片方だけ更新されると不整合が発生する |
| Template | Template + Field | テンプレートと項目は一体で管理する<br>片方だけ更新されると不整合が発生する  |

## トランザクションが必要な操作

以下の操作では、トランザクションが必要。

### 1. 集約の作成

* Template作成

  * `template` + `fields` を同時作成する。
* Note作成

  * `note` + `sections` を同時作成する。

### 2. 集約の更新

* Template更新

  * 存在確認
  * `template` + `fields` の更新
* Note更新

  * 存在確認
  * `note` + `sections` の更新

### 3. 集約の削除

* Template削除

  * 使用チェック
  * `template` + `fields` の削除
* Note削除

  * 存在確認
  * `note` + `sections` の削除

### 4. 状態変更

* Note公開／非公開

  * 権限チェック
  * `note` の更新（`status`、`updatedAt`）

> 状態変更で実際に書き換わるのは`note`のみだが、集約単位で整合性を守るため、
> 他のNote操作と同じくトランザクション内で行う。

## トランザクション不要な操作

以下の操作では、トランザクションは不要。

### 1. 読み取り専用のクエリ

* Template一覧取得
* Note一覧取得
* Account取得

### 2. 単一エンティティの操作

* Accountのプロフィール更新

  * 単一テーブルの更新
